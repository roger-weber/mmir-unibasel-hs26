Low-Dimensional Search Structures

A city has a few dozen post offices, and a resident wants to know which one is closest to home. This is the nearest-neighbor problem of the previous section in two dimensions, and Donald Knuth used exactly this scenario to name it: the post-office problem. In two dimensions the problem is easy, and its solution has been known for a long time. This section follows how the solutions for two and three dimensions grew from a precomputed map of all answers into tree structures, and why the hope of searching in logarithmic time, as a B-tree does for one-dimensional keys, was never quite fulfilled.

Precomputing all answers: Voronoi diagrams¶

For the post-office problem, we can draw a map that answers every possible query in advance. Around each post office, we mark the region of all locations that are closer to this office than to any other. The result is a Voronoi diagram: a partition of the space into one cell per stored point, as shown in Figure 1. To answer a query, we locate the cell that contains the resident’s home and return the post office of that cell.

The Voronoi diagram inverts the search problem. Instead of searching for the nearest neighbor of one query, it computes the nearest neighbor of all possible queries at once and stores the answers as regions. This is the geometric analogue of the inverted file. An inverted file precomputes the result of every single-term query; a Voronoi diagram precomputes the result of every nearest-neighbor query. The idea is not tied to Euclidean distance: Voronoi diagrams exist for other distance measures as well.

The difficulty lies in building and storing the cells. In two dimensions, the diagram of nnn points has a size proportional to nnn. In ddd dimensions, its worst-case size grows like n⌈d/2⌉n^{⌈d/2⌉}n⌈d/2⌉, so already in three dimensions it can grow quadratically, and finding the cell that contains a query becomes as hard as the search it was meant to replace. A common workaround approximates each cell by its minimum bounding rectangle, but the rectangles of neighboring cells overlap, so a query must check several candidates instead of one. Insertions and deletions are awkward too, since one new point reshapes all neighboring cells. Voronoi diagrams remain the clearest mental model of exact nearest-neighbor search, but not a practical index beyond a few dimensions.

From B-trees to spatial indexes¶

Spatial search is much older than embeddings. Geographic information systems, computer-aided design, and image databases needed it from the 1970s onward, and the research followed a familiar path. It started with simple partitions of space and moved on to tree structures, in the hope of repeating for two and three dimensions what the B-tree achieves for one-dimensional keys: finding any entry in a logarithmic number of steps.

These structures were designed for range search first. A range query asks for all points within a region, for example all points within distance rrr of the query q\mathbf{q}q, as in Figure 2, or all points inside a map window. The region is known before the search starts, so the index only needs to identify the parts of the space that overlap it.

The grid file is the simplest such structure. It lays a grid over the space, chooses the grid lines so that each cell holds roughly the same number of points, and stores the points of each cell on a disk page, as shown in Figure 3. A directory maps every cell to its page. A range query reads only the pages of the cells that overlap the query region. In two dimensions, a small query window needs only a few page reads, however large the collection is.

How a grid file grows (optional reading)

The grid lines of a grid file are not equally spaced. They are placed so that the resulting disk pages hold roughly the same number of points, which keeps the cost of reading a page predictable.

The directory associates each grid cell with the disk page that holds its points. Many cells stay empty or nearly empty when the data is unevenly distributed, so several cells may share one disk page. This keeps the number of pages close to the minimum needed for the data.

When an insertion fills a page that serves several cells, the grid file creates a new page and distributes the cells evenly between the two pages. Only the directory entries of these cells change. When a single cell grows too large for one page, the grid file adds a new partition line along a chosen dimension. This splits every cell that the line crosses and enlarges the directory, but again only the points of the overflowing cell move to new pages.

The directory is also the grid file’s weakness. Splitting each of ddd dimensions only once already produces 2d2^{d}2d cells. For the 48-dimensional color histograms of the previous section this is 248≈2.8×10142^{48} \approx 2.8 \times 10^{14}248≈2.8×1014 cells, almost all of them empty, and the directory no longer fits in memory.

R-trees and the problem of overlap¶

The R-tree carries the idea of the B-tree directly into the multi-dimensional space. It groups nearby points into a minimum bounding rectangle (MBR), groups nearby rectangles into larger rectangles, and continues up to a single root. Figure 4 shows a small R-tree. Like a B-tree, it is balanced: all leaves are at the same depth, and every node holds between a minimum and a maximum number of entries. When a node overflows, it is split into two nodes, and the split may propagate up to the root. R-trees index points, rectangles, and polygons, and they are a mainstay of spatial databases to this day.

Splitting a leaf is easy. We divide its points at the median of one dimension, and the two new rectangles do not overlap. Splitting an inner node is harder, because its entries are rectangles, not points, and two groups of rectangles often cannot be separated cleanly. Figure 5 shows the possible outcomes: a clean split, a split whose rectangles overlap, and a split where one rectangle lies completely inside the other.

Overlap also grows over time. When a new point falls into the overlap of two rectangles, as in Figure 6, the insertion must choose a path. The usual heuristic follows the child whose rectangle needs the least enlargement. A poor choice inflates a rectangle, which then overlaps its neighbors even more and makes the next decision harder. Every query that reaches an overlapping region must follow several branches, and the tree loses the single root-to-leaf path that makes a B-tree fast.

A second problem is less visible but more fundamental: nearest-neighbor search is not a range search. A range query knows its region in advance. A nearest-neighbor query does not know how far away its answer lies. It must find a candidate and then prove that no other point is closer. If the query lies near the border of a leaf, the closest point may well sit in a neighboring leaf, possibly in a different subtree, and the search has to look there before it can stop. Even without any overlap, a nearest-neighbor search therefore tends to visit more than one path from the root to the leaves.

An optimal nearest-neighbor algorithm¶

Hjaltason and Samet proposed a nearest-neighbor algorithm that works for any structure that divides the space into nested regions: grid files, R-trees, and their many variants. It is optimal in a precise sense. It finds the nearest neighbor and proves that no other point is closer, and no correct algorithm can do this with fewer node inspections.

The algorithm keeps a priority queue of nodes and points, ordered by their distance to the query q\mathbf{q}q. For a point, this is the exact distance. For a node, it is a lower bound: the smallest distance that any point inside the node’s region could have.

insert the root into the queue with its lower bound
while the queue is not empty:
    remove the entry e with the smallest distance
    if e is a data point:   return e as the nearest neighbor
    if e is a leaf:         insert every point of e with its distance to q
    if e is an inner node:  insert every child of e with its lower bound

The algorithm only needs two primitives: the distance between the query and a point, and a lower bound for the distance between the query and a region. For a rectangle and Euclidean distance, the lower bound is the distance to the closest point of the rectangle.

The example shows the cost structure of every tree-based nearest-neighbor search. The search visited both inner nodes and two leaves, twice as many as a single root-to-leaf path. Because the algorithm is optimal, nothing can be done about this: any correct algorithm must open L3, since a point within distance 1.00 of the query could have been there. The extra paths are the price of proving the answer, not a weakness of the algorithm.

Why the algorithm is correct and optimal (optional reading)

Correctness. The queue orders its entries by increasing distance. Every child of a node lies inside the node’s region, so its lower bound is at least as large as the node’s lower bound, and every point inside a region is at least as far away as the region’s lower bound. When a data point reaches the front of the queue, every entry still in the queue, and every descendant of these entries, is at least as far from the query as this point. No closer point can remain hidden, so the point at the front is the nearest neighbor.

Optimality. Suppose we already knew the nearest neighbor of q\mathbf{q}q. The NN-sphere is the sphere centered at q\mathbf{q}q that passes through this nearest neighbor, drawn in Figure 7. Any node whose region intersects the NN-sphere might contain a closer point, so any correct algorithm must inspect it; skipping it would leave the answer unproven. A node whose region lies entirely outside the NN-sphere cannot contain a closer point and need not be inspected.

The algorithm inspects nodes in increasing order of their lower bounds and stops as soon as the nearest neighbor reaches the front of the queue. At that moment, it has inspected exactly the nodes whose lower bound is at most the nearest-neighbor distance, which are the nodes whose regions intersect the NN-sphere. It therefore inspects no node that a correct algorithm could skip. In the example above, the NN-sphere has radius 1.44 and intersects A, B, L1, and L3, which are exactly the nodes the search opened.

The same argument extends to the kkk nearest neighbors, with the sphere passing through the kkk-th nearest neighbor.

Beyond Euclidean distance: dot product and cosine¶

The algorithm never looks inside the distance function. It needs a bound for each region that is optimistic, meaning it never promises less than the region could deliver. For a distance, this is a lower bound; for a similarity score, it is an upper bound, and the queue is ordered by decreasing score instead of increasing distance. Figure 8 shows both cases.

Ram and Gray used this bound to run exact maximum-inner-product search on ball trees.

So do these structures work with dot product and cosine out of the box? Largely yes, with a few caveats.

  • Grid files and R-trees work with the dot product as soon as the bound function is replaced. Nested rectangles keep the property the algorithm relies on: a child’s bound never exceeds its parent’s bound. Correctness is therefore guaranteed. Efficiency is not, because the split and insertion heuristics were designed to keep rectangles small under Euclidean distance, not to group vectors that score similarly.

  • Cosine similarity needs no special treatment. After normalizing the stored vectors, ranking by cosine equals ranking by Euclidean distance, as the previous section showed. Any Euclidean index can be used unchanged.

  • Metric trees such as the M-tree prune with the triangle inequality. The dot product is not a metric, so these structures cannot use it directly. With cosine, they can again work on the Euclidean distance between normalized vectors.

  • Voronoi diagrams change their character. Under the dot product, a point is not necessarily its own best match: for p=(1,1)\mathbf{p} = (1, 1)p=(1,1), the longer vector (2,2)(2, 2)(2,2) scores 4 against p\mathbf{p}p, while p\mathbf{p}p scores only 2 against itself. Only the vertices of the convex hull of the collection can be the best match of any query; all other points have empty cells.

There is also a general trick that turns maximum-inner-product search into nearest-neighbor search. Let MMM be the largest vector length in the collection. Appending the component M2−∥pi∥2\sqrt{M^2 - \lVert \mathbf{p}_i \rVert^2}M2−∥pi​∥2​ to every stored vector and 0 to the query gives all stored vectors the same length MMM. The squared Euclidean distance between the extended vectors is then ∥q∥2+M2−2 q⋅pi\lVert \mathbf{q} \rVert^2 + M^2 - 2\, \mathbf{q} \cdot \mathbf{p}_i∥q∥2+M2−2q⋅pi​, so the nearest neighbor is exactly the vector with the largest dot product, and any Euclidean index can answer the query.

A fundamental limit¶

In two and three dimensions, the extra paths are a small price. A nearest-neighbor search opens a few more leaves than a range search would, and the structures easily beat a full scan. Research in the 1990s, however, showed that the price grows with the number of dimensions. Rectangles overlap more, the nearest neighbor lies farther away, and the NN-sphere intersects more and more leaves, until the optimal algorithm visits almost all of them.

The research community responded with a long series of new structures. They changed the shape of the bounding regions to spheres or combinations of spheres and rectangles, introduced split strategies that reduce overlap, enlarged nodes when splitting did not pay off, or replaced the data-space metric by an object metric such as edit distance. Notable examples include the R+-tree (1987), R*-tree (1990), TV-tree (1994), vp-tree (1993), GiST (1995), X-tree (1996), SS-tree (1996), SR-tree (1997), M-tree (1997), and Pyramid-tree (1998), and many more followed. Each improved on its predecessors for some data and some dimensions. None of them restored logarithmic search in high dimensions.

That so many clever designs failed in the same way suggests that the problem lies not in any single structure but in high-dimensional space itself. The effect is known as the curse of dimensionality, a term originally coined by Richard Bellman. The next section explains what makes high-dimensional spaces so hostile to search.
