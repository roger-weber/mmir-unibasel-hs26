Vector Search in Practice

The methods of the previous section rarely reach an application in raw form. They arrive packaged inside libraries, search engines, and databases that also handle storage, updates, and scale. This section follows one realistic query through four widely used systems: the FAISS library, the Lucene library, the OpenSearch engine, and the pgvector extension for PostgreSQL. We first look at how each system answers the vector part of the query, and then at how each one adds metadata filters and keyword search.

A running example: movie search¶

The movie table of Practical Frameworks stored a title, an overview, a rating, and a year for every movie. We extend it with two text fields, the main actors and the genres, and with an embedding of the overview, computed by an embedding model as in Building Semantic Search. With a model such as Qwen3-Embedding-0.6B, every movie receives a vector with 1,024 dimensions. A user now types:

a mind-bending heist thriller with Leonardo DiCaprio, released after 2005, rated 7.5 or better

No single retrieval method covers this request. Each part of it asks for a different kind of match:

The overview of Inception describes a thief who steals secrets by entering the dreams of his targets. It contains neither “mind-bending” nor “heist”, so BM25 on the overview would miss it. An embedding does better, but not well enough on its own: among 10,000 movies embedded with Qwen3-Embedding-0.6B, the vector search alone ranks Inception only 138th, behind movies whose overviews match “heist thriller” more literally. Names behave the other way round. An embedding blurs “Leonardo DiCaprio” into a region of similar actors, while BM25 matches the name exactly. The year and the rating are not matters of degree at all: a movie from 2001 must not appear, however similar it is. Each ingredient matters. The filters on year and rating lift Inception to second place among the 261 admitted movies, and fusing the vector ranking with BM25 on the actors puts it first. The rest of this section builds this query step by step: first the vector search, then the filters and the keyword search.

Vector search in four systems¶

FAISS: a library of vector indexes¶

FAISS (Facebook AI Similarity Search), developed at Meta, is a C++ library with Python bindings that runs on CPUs and GPUs. It implements all methods of the previous section and lets us combine them freely through index type strings. FAISS stores only vectors and their integer identifiers. The titles, the actors, and the years stay in the application’s own data store, and the application maps the returned identifiers back to movies.

import faiss
import numpy as np

# 1. Movie embeddings (one row per movie) and their movie ids
X = np.load("overview_embeddings.npy").astype("float32")   # shape (n, 1024)
ids = np.load("movie_ids.npy").astype("int64")
faiss.normalize_L2(X)               # unit length: inner product = cosine

# 2. Build an IVF index with PQ codes (lever 3 + lever 2)
index = faiss.index_factory(1024, "IVF256,PQ64", faiss.METRIC_INNER_PRODUCT)
index.train(X)                      # k-means for the centers and the codebooks
index.add_with_ids(X, ids)

# 3. Search: embed the query and probe 16 of the 256 lists
q = embed("a mind-bending heist thriller").reshape(1, -1)
faiss.normalize_L2(q)
index.nprobe = 16
scores, movie_ids = index.search(q, 10)

Step 1 normalizes the vectors, so that the inner product equals the cosine similarity. Step 2 builds the composite index of the previous section: train runs k-means to find the 256 centers of the inverted file and the codebooks of the product quantizer, and add_with_ids encodes every vector into 64 one-byte codes. Step 3 sets the tuning knob nproben_{\text{probe}}nprobe​ and returns the ten best movie ids with their approximate scores. Changing the index string, for example to HNSW32 or to IVF256,PQ64,RFlat with an exact refinement stage, changes the method without changing the rest of the code.

Lucene: vectors next to the inverted index¶

Lucene stores vectors as one more field type of a document. The document of Practical Frameworks receives a KnnFloatVectorField next to its text and numeric fields:

// 1. A movie document with text, numeric, and vector fields
Document doc = new Document();
doc.add(new TextField("title", "Inception", Field.Store.YES));
doc.add(new TextField("actors", "Leonardo DiCaprio, Joseph Gordon-Levitt", Field.Store.NO));
doc.add(new TextField("genres", "Thriller, Science Fiction", Field.Store.NO));
doc.add(new IntField("year", 2010, Field.Store.YES));
doc.add(new FloatField("rating", 8.8f, Field.Store.YES));
doc.add(new KnnFloatVectorField("embedding", embedding,     // float[1024]
    VectorSimilarityFunction.COSINE));
writer.addDocument(doc);

// 2. Approximate k-NN query on the vector field
float[] query = embed("a mind-bending heist thriller");
Query knn = new KnnFloatVectorQuery("embedding", query, 10);
TopDocs top = searcher.search(knn, 10);

Lucene builds an HNSW graph for the vector field of every segment. A query searches the graph of each segment and merges the per-segment results, the same scatter-gather pattern as for text queries. Because segments are merged in the background, their graphs must be merged as well, which makes indexing vectors considerably more expensive than indexing text. Lucene reports cosine similarity as a score in [0,1][0, 1][0,1], computed as (1+cos⁡)/2(1 + \cos)/2(1+cos)/2, so that higher always means better. For lever 2, Lucene offers vector formats that quantize the stored vectors to 7 or 4 bits per component, or to a single bit. The full vectors stay in the index, so the best candidates can be rescored with them: since version 10.3, the RescoreTopNQuery does this inside Lucene; in earlier versions, the application rescores.

OpenSearch: distributed vector search¶

OpenSearch wraps Lucene in a distributed engine, as described in Scaling Out. Vector search is a field type of the index mapping. The knn_vector field declares the dimensions, the similarity, and the ANN method:

# 1. Index mapping: text fields, numeric fields, and a vector field
client.indices.create(index="movies", body={
    "settings": {"index": {"knn": True}},
    "mappings": {"properties": {
        "title":   {"type": "text"},
        "actors":  {"type": "text"},
        "genres":  {"type": "text"},
        "year":    {"type": "integer"},
        "rating":  {"type": "float"},
        "embedding": {
            "type": "knn_vector",
            "dimension": 1024,
            "space_type": "cosinesimil",
            "method": {"name": "hnsw", "engine": "faiss",
                       "parameters": {"m": 16, "ef_construction": 128}},
        },
    }},
})

# 2. Approximate k-NN query
query = embed("a mind-bending heist thriller")
response = client.search(index="movies", body={
    "size": 10,
    "query": {"knn": {"embedding": {"vector": query, "k": 10}}},
})

The engine parameter selects the implementation behind the field. The Lucene engine uses Lucene’s own HNSW graphs; the FAISS engine runs FAISS inside every shard and also offers IVF and product quantization. The parameters m and ef_construction are the HNSW parameters of the previous section. A query is sent to every shard, each shard searches its own index and returns its own top kkk, and a coordinating node merges the shard results. The global top kkk is always among the per-shard lists, so merging adds no error of its own; the approximation comes only from the ANN search inside each shard. The price is that every query must visit every shard.

pgvector: vectors in SQL¶

The pgvector extension adds a vector column type to PostgreSQL. We extend the movie table with a vector column and an HNSW index:

-- 1. Enable the extension and add a vector column
CREATE EXTENSION IF NOT EXISTS vector;
ALTER TABLE movies ADD COLUMN embedding vector(1024);

-- 2. Approximate index: HNSW with cosine distance
CREATE INDEX ON movies USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- 3. k-NN query: order by cosine distance to the query embedding
SET hnsw.ef_search = 100;
SELECT title, year, embedding <=> '[0.021, -0.013, ...]' AS distance
FROM movies
ORDER BY embedding <=> '[0.021, -0.013, ...]'   -- 1,024 values
LIMIT 10;

pgvector works with distances: smaller is better. The operator <=> computes the cosine distance 1−cos⁡1 - \cos1−cos, <-> the Euclidean distance, <+> the Manhattan distance, and <#> the negative dot product, negated to fit the same convention. Without an index, the query scans all rows and returns exact results. With the HNSW index of step 2, PostgreSQL’s planner uses the index for the ORDER BY ... LIMIT pattern. The index parameters are m (default 16) and ef_construction (default 64); the query parameter hnsw.ef_search (default 40) sets the candidate list length. The second index type, IVFFlat, is an inverted file with exact vectors in its lists, with lists centers and ivfflat.probes probed lists (default 1).

pgvector also exposes the other two levers. A halfvec column stores 16-bit floats. The function binary_quantize reduces every component to its sign bit, compared with the Hamming distance operator <~>. An index on subvector(embedding, 1, 256) searches only the leading 256 components of a Matryoshka embedding. The refine step is plain SQL: an inner query retrieves candidates through a compact index, and an outer query reorders them by the full vectors.

-- Binary codes for the candidate search, full vectors for the final order
CREATE INDEX ON movies
  USING hnsw ((binary_quantize(embedding)::bit(1024)) bit_hamming_ops);

SELECT title FROM (
  SELECT title, embedding FROM movies
  ORDER BY binary_quantize(embedding)::bit(1024)
           <~> binary_quantize('[0.021, ...]'::vector)
  LIMIT 100                                     -- k' = 100 candidates
) AS candidates
ORDER BY embedding <=> '[0.021, ...]'
LIMIT 10;

Adding filters and keyword search¶

The vector query finds movies with mind-bending heist plots, but it ignores the rest of the request. We now add the filters on year and rating and the keyword part for the actor and the genre.

Three ways to filter¶

Combining a filter with a vector search is harder than it looks, because the ANN index knows nothing about the metadata. There are three strategies.

Pre-filtering applies the metadata condition first and then compares the query exactly with the vectors that pass. The result is exact, and the cost depends on how many vectors pass. A selective filter makes this cheap: if a filter admits 0.01% of the billion vectors of the previous section, an exact scan over the 100,000 survivors reads only 300 MB. A mild filter makes it expensive, because the scan over the survivors approaches a full scan.

Post-filtering runs the ANN search first and discards the results that fail the filter. This keeps the index intact, but it can return too few results. With HNSW and the default hnsw.ef_search of 40, a pgvector index scan delivers about 40 candidates. If the filter matches 10% of the rows, only about 4 of them survive, even if the query asked for 10. A fixed over-fetch, retrieving more candidates than requested, helps only if we guess the selectivity right. The robust form treats the index as a stream of candidates in order of increasing distance, like the incremental nearest-neighbor algorithm of Low-Dimensional Search Structures: the filter consumes candidates from the stream until kkk of them pass. HNSW suits this form well. Its search already maintains a queue of candidates, and continuing the search simply extends the queue into regions further away from the query. pgvector’s iterative index scans work this way.

Post-filtering can silently return too few results

If a query asks for the ten nearest neighbors and then removes those failing a selective filter, the final list may contain far fewer than ten items, or be empty, even though many matching documents exist deeper in the ranking. Over-fetch a larger candidate set before filtering, and verify that enough results survive.

Filtering during the search evaluates the filter first, for example as a bitmap over all document ids, and passes it to the ANN search, which only accepts admitted documents as results. This fits the inverted file particularly well. An IVF search with PQ codes scans the lists of the probed centers entry by entry anyway; checking each entry against the bitmap costs one bit lookup and lets the scan skip the distance computation for every non-admitted vector. The search itself does not change, only its result is restricted. In the billion-vector example with 16 of 4,096 lists probed, the scan visits about 3.9 million codes. If the filter admits 1% of the collection, about 39,000 of these are admitted, far more than needed for a top 10.

The limit lies in very selective filters. If the filter admits only 0.001% of the collection, the probed lists contain about 39 admitted vectors, and the ten best of them may be poor matches, because the good admitted matches lie in lists that were not probed. Probing more lists helps, but at this selectivity the 10,000 admitted vectors fit into an exact scan of 30 MB, which is both cheaper and exact. Systems that filter during the search therefore choose per query: if only a few documents pass the filter, they skip the index and fall back to pre-filtering with an exact scan. Graph indexes can filter during the search as well, but they must still step through non-matching nodes, because these can lie on the path to a matching one. With a selective filter, most steps of the graph search are wasted.

Keyword search adds a second ranking. Building Semantic Search fused a BM25 ranking and a dense ranking with reciprocal rank fusion (RRF) in Pipeline D. RRF needs only ranks, so it fuses a cosine similarity and a BM25 score without calibrating them against each other. The four systems differ in which strategy they use for filters and in how much of the fusion they provide.

FAISS¶

FAISS has no metadata, so the application evaluates the filter on its own data and passes the admitted ids to the search. An IDSelector makes the index skip all other ids while it scans the probed lists, which is filtering during the search. With a selective filter, the probed lists may contain fewer than ten admitted movies, so it pays to raise nproben_{\text{probe}}nprobe​ or to switch to an exact scan over the admitted vectors. FAISS has no keyword search either. A separate engine computes the BM25 ranking, and the application fuses the two rankings:

# 1. Filter in the application, then search only the admitted ids
admitted = movies.query("year > 2005 and rating >= 7.5")["id"].to_numpy()
params = faiss.SearchParametersIVF(sel=faiss.IDSelectorBatch(admitted), nprobe=32)
_, dense_ids = index.search(q, 50, params=params)

# 2. BM25 ranking from a keyword engine, restricted to the same ids
sparse_ids = bm25_search('actors:"leonardo dicaprio" genres:thriller', admitted, 50)

# 3. Reciprocal rank fusion of the two rankings
def rrf(*rankings, k=60):
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

top10 = rrf(dense_ids[0], sparse_ids)[:10]

Lucene¶

Lucene filters during the search. The filter is passed as the fourth argument of KnnFloatVectorQuery. Lucene evaluates it per segment and searches the graph only for admitted documents. If fewer documents pass the filter than the query asks for, it runs an exact search instead, and if the graph search visits too many vectors without completing, it stops and switches to an exact search as well. The keyword part becomes ordinary BM25 clauses of a Boolean query:

// 1. Filter on year and rating (FILTER clauses do not score)
Query filter = new BooleanQuery.Builder()
    .add(IntField.newRangeQuery("year", 2006, Integer.MAX_VALUE), Occur.FILTER)
    .add(FloatField.newRangeQuery("rating", 7.5f, Float.POSITIVE_INFINITY), Occur.FILTER)
    .build();

// 2. Vector query that applies the filter during the graph search
Query knn = new KnnFloatVectorQuery("embedding", query, 50, filter);

// 3. Hybrid query: vector score + BM25 on actors and genres
Query hybrid = new BooleanQuery.Builder()
    .add(knn, Occur.SHOULD)
    .add(new PhraseQuery("actors", "leonardo", "dicaprio"), Occur.SHOULD)
    .add(new TermQuery(new Term("genres", "thriller")), Occur.SHOULD)
    .add(filter, Occur.FILTER)
    .build();
TopDocs top = searcher.search(hybrid, 10);

Two details matter here. First, the filter belongs inside the vector query. Adding it only as a FILTER clause of the Boolean query, next to an unfiltered KnnFloatVectorQuery, runs the two parts independently: the vector query returns its top 50 over all movies, and the Boolean query intersects them with the filter. This is post-filtering, with all its risks. Second, a Boolean query adds the scores of its clauses. The vector clause contributes at most 1, while a BM25 clause for a rare name can contribute several points, so the keyword part tends to dominate. Lucene itself provides no rank fusion; applications either weight the clauses with boosts or run the two queries separately and fuse their rankings with RRF.

OpenSearch¶

OpenSearch passes a filter inside the knn clause to the engine, which then filters during the search in the same way as Lucene. For the keyword part, a hybrid query runs its sub-queries separately, and a search pipeline fuses their results. Since version 2.19, the score-ranker-processor implements RRF:

# 1. Search pipeline that fuses the sub-query rankings with RRF
client.transport.perform_request("PUT", "/_search/pipeline/rrf-pipeline", body={
    "phase_results_processors": [{"score-ranker-processor": {
        "combination": {"technique": "rrf", "rank_constant": 60}}}],
})

# 2. Hybrid query: BM25 on actors and genres, k-NN on the overview,
#    both restricted by the same filter on year and rating
filters = {"bool": {"filter": [
    {"range": {"year": {"gt": 2005}}},
    {"range": {"rating": {"gte": 7.5}}},
]}}
response = client.search(index="movies", params={"search_pipeline": "rrf-pipeline"},
    body={"size": 10, "query": {"hybrid": {
        "queries": [
            {"bool": {"should": [
                {"match_phrase": {"actors": "Leonardo DiCaprio"}},
                {"match": {"genres": "thriller"}},
            ]}},
            {"knn": {"embedding": {"vector": query, "k": 50}}},
        ],
        "filter": filters,
    }}})

The filter of the hybrid query applies to both sub-queries. Instead of RRF, the pipeline can also use a normalization-processor, which rescales the scores of each sub-query to a common range and then combines them with weights. This keeps more information than ranks alone, at the cost of choosing a normalization and the weights.

pgvector¶

In SQL, the filter is an ordinary WHERE clause. With an approximate index, PostgreSQL applies it after the index scan, which is post-filtering with the risk described above. Since version 0.8, pgvector’s iterative index scans continue through the index until enough rows pass the filter. The keyword part uses PostgreSQL’s full-text search from Practical Frameworks, and the fusion is written in SQL:

-- 1. Filtered vector search; continue the index scan until enough rows pass
SET hnsw.iterative_scan = relaxed_order;

-- 2. Hybrid search: dense and sparse rankings, fused with RRF (k = 60)
WITH dense AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> '[0.021, ...]') AS r
  FROM movies
  WHERE year > 2005 AND rating >= 7.5
  ORDER BY embedding <=> '[0.021, ...]'
  LIMIT 50
),
sparse AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank(tsv, q) DESC) AS r
  FROM movies, to_tsquery('(leonardo <-> dicaprio) | thriller') AS q
  WHERE tsv @@ q AND year > 2005 AND rating >= 7.5
  ORDER BY ts_rank(tsv, q) DESC
  LIMIT 50
)
SELECT m.title,
       COALESCE(1.0 / (60 + d.r), 0) + COALESCE(1.0 / (60 + s.r), 0) AS rrf
FROM dense d
FULL OUTER JOIN sparse s ON d.id = s.id
JOIN movies m ON m.id = COALESCE(d.id, s.id)
ORDER BY rrf DESC
LIMIT 10;

Here the tsv column covers the actors and the genres in addition to the title and the overview. The dense part ranks the admitted movies by cosine distance, the sparse part ranks the movies that match the actor or the genre by ts_rank, and the final query adds the RRF contributions of both rankings. A movie found by only one of the two rankings receives a contribution of zero from the other. As noted in Practical Frameworks, ts_rank is not BM25, but RRF only uses the order of the sparse ranking, which makes the difference smaller.

Choosing a system¶

The four systems implement the same methods but serve different settings. FAISS gives the most control over the index and the highest speed, including on GPUs, but it handles only vectors: filters, keyword search, storage, and updates remain the application’s job. Lucene keeps vectors, text, and metadata in one index and filters during the search, which suits Java applications that embed their search. OpenSearch adds distribution across many machines and a complete hybrid pipeline with filters and rank fusion, at the price of operating a cluster. pgvector keeps vectors next to the relational data, with SQL filters, joins, and transactions, and suits collections that fit on a single database server. Dedicated vector databases, such as Milvus, Qdrant, and Weaviate, follow the same patterns, and several of them appear in the benchmark of the previous section.

Whatever the system, the query of this section needs the same three ingredients: an approximate vector search for the meaning, a keyword search for names and terms, and filters for the hard constraints. What differs is how much of the combination the system does for us.
