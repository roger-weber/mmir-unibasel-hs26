Approximate Nearest-Neighbor Search

A retrieval system rarely shows the raw output of a vector search to its users. In Semantic Similarity with Transformers, embeddings served as a first stage: a bi-encoder retrieves a few hundred candidates, and a cross-encoder reorders them with a stronger and more expensive model. Media retrieval follows the same pattern. A compact color feature finds candidate images, and a more detailed comparison puts them in their final order. For such a first stage, the exact nearest neighbor has no special value. What matters is that the good matches are among the candidates, because the second stage decides their order.

Even without a second stage, users want to see good matches, not necessarily the single best one. The previous section showed that high dimensions reduce contrast: the nearest neighbor is only marginally closer than the next few points, and all of them stand out clearly from the background. Returning the third-best match instead of the best one hardly changes what the user sees. This opens the door to a trade: we give up exactness and gain speed.

What carries over from the previous section

  • High dimensions defy 2D intuition: distances grow like d\sqrt{d}d​, while their spread stays the same. The contrast between the nearest and the farthest point vanishes, (δmax⁡−δmin⁡)/δmin⁡→0(\delta_{\max} - \delta_{\min}) / \delta_{\min} \to 0(δmax​−δmin​)/δmin​→0, and dot products of random vectors concentrate around zero. This holds for Euclidean distance, dot product, and cosine alike.

  • Trees can no longer prune: beyond a few dozen dimensions, the sphere around the query that passes through its nearest neighbor intersects every leaf, so even the optimal search algorithm reads all the data. In practice, a full scan is faster than a tree index beyond roughly ten dimensions.

  • Real data still works: related items form clusters, and good matches stand out clearly from a background in which everything else appears equally far away.

For the full background, see The Curse of Dimensionality.

How can we accelerate the search? A full scan reads every vector, so its cost is the number of vectors times the size of each vector. A concrete collection makes this tangible. One billion embeddings with 768 dimensions, stored as 4-byte floats, occupy 109×768×410^9 \times 768 \times 4109×768×4 bytes, about 3 TB. A full scan reads all 3 TB for every query. There are three levers to reduce this volume, and this section treats them in turn:

  1. Fewer dimensions: map the vectors into a lower-dimensional space.

  2. Fewer bits per vector: store each vector as a compact code.

  3. Fewer vectors read: visit only the part of the collection near the query.

Each lever trades a little accuracy for speed. Combined, they reduce the work per query by two to three orders of magnitude.

Fewer dimensions¶

The first lever shrinks every vector before the search starts. Principal component analysis (PCA) finds the directions along which the data varies most and projects every vector onto the leading ones. It works well when the original dimensions are not independent. The color histogram of Distance and Similarity Measures is a good case. Neighboring bins cover similar intensities, so a slightly brighter photograph moves pixels from one bin into the next. Correlated dimensions carry overlapping information, and a few principal components capture most of it. Distances in the reduced space then approximate the distances in the original space well.

Embeddings can be trained for this purpose. The Matryoshka embeddings of Building Semantic Search arrange their information so that the leading dimensions carry the most significant part, and a prefix of the vector is itself a usable embedding. Truncation needs no projection at all, only a shorter read.

Dimensionality reduction is a modest lever. Depending on the features, it removes roughly 20 to 60 percent of the data without changing the results much. Reducing our example collection from 768 to 384 dimensions halves 3 TB to 1.5 TB. Every vector must still be read, so the search remains a full scan, only a cheaper one.

Fewer bits per vector¶

The second lever keeps the dimensions but stores each vector with fewer bits. A float uses 32 bits per component, far more precision than a similarity comparison needs. The errors that compression introduces are small compared to the gap between good matches and the background, so they rarely change which matches stand out.

Scalar quantization¶

The simplest form replaces each float with a small integer. We divide the value range of each dimension into 2b2^b2b intervals and store only the number of the interval that contains the value. With b=8b = 8b=8, every component becomes one byte, and the vector shrinks by a factor of 4. With b=4b = 4b=4, as in the FAISS index type SQ4, it shrinks by a factor of 8. Distances computed on the interval numbers are approximations of the true distances.

Quantization does not have to give up exactness. The vector approximation file (VA-file) of Weber, Schek, and Blott (1998) accepts the conclusion of the previous section: if every leaf must be read anyway, make reading cheaper. The interval numbers of a vector describe a cell of a grid, and from the cell we can compute a lower and an upper bound on the distance between the query and any vector inside it. The search first scans the compact approximations and discards every vector whose lower bound exceeds the kkk-th smallest upper bound. Only the few remaining candidates are read in full and compared exactly. The result is exact, while the scan reads only a fraction of the data. Skipping the exact comparisons turns the same codes into an approximate method. Scalar quantization is therefore the bridge between exact and approximate search.

Consider two dimensions with values in [0,1][0, 1][0,1] and b=2b = 2b=2 bits per dimension. Each dimension splits into four intervals of width 0.25, and every vector is stored as two 2-bit numbers. The vector p=(0.62,0.10)\mathbf{p} = (0.62, 0.10)p=(0.62,0.10) lies in interval 2 of the first dimension, [0.50,0.75][0.50, 0.75][0.50,0.75], and in interval 0 of the second, [0,0.25][0, 0.25][0,0.25], so its approximation is the code (10,00)(10, 00)(10,00).

For the query q=(0.20,0.55)\mathbf{q} = (0.20, 0.55)q=(0.20,0.55), the code alone bounds the distance. In the first dimension, any value in [0.50,0.75][0.50, 0.75][0.50,0.75] lies at least 0.50−0.20=0.300.50 - 0.20 = 0.300.50−0.20=0.30 and at most 0.75−0.20=0.550.75 - 0.20 = 0.550.75−0.20=0.55 from q1q_1q1​. In the second dimension, any value in [0,0.25][0, 0.25][0,0.25] lies at least 0.55−0.25=0.300.55 - 0.25 = 0.300.55−0.25=0.30 and at most 0.55−0=0.550.55 - 0 = 0.550.55−0=0.55 from q2q_2q2​. Combining the two dimensions gives 0.302+0.302≈0.42\sqrt{0.30^2 + 0.30^2} \approx 0.420.302+0.302​≈0.42 as the lower bound and 0.552+0.552≈0.78\sqrt{0.55^2 + 0.55^2} \approx 0.780.552+0.552​≈0.78 as the upper bound. The exact distance, 0.422+0.452≈0.62\sqrt{0.42^2 + 0.45^2} \approx 0.620.422+0.452​≈0.62, lies between them.

The search runs in two phases. The filtering phase scans all approximations, computes both bounds for each, and keeps track of the kkk smallest upper bounds. A vector whose lower bound exceeds the kkk-th smallest upper bound cannot be among the kkk nearest neighbors and is discarded. The refinement phase visits the remaining candidates in order of increasing lower bound, reads their exact vectors, and computes their true distances. It stops as soon as the next lower bound exceeds the kkk-th smallest true distance found so far, because no later candidate can be closer.

Both phases are exact, so the result is exact. The gain comes from the size of the approximations: with 4 to 8 bits per dimension, the filtering phase reads 4 to 8 times less data than a full scan, and only a small number of exact vectors is read in the refinement phase. Because the scan is sequential, it also avoids the random disk accesses of a tree index.

Product quantization¶

Scalar quantization treats every dimension separately and needs at least one bit per dimension. Product quantization (PQ), introduced by Jégou, Douze, and Schmid (2011), quantizes groups of dimensions together. Figure 1 shows the idea for the eight-dimensional vector (0.1,0.3,0.5,0.2,0.6,0.4,0.9,0.8)(0.1, 0.3, 0.5, 0.2, 0.6, 0.4, 0.9, 0.8)(0.1,0.3,0.5,0.2,0.6,0.4,0.9,0.8). We split it into m=4m = 4m=4 sub-vectors of two components each: (0.1,0.3)(0.1, 0.3)(0.1,0.3), (0.5,0.2)(0.5, 0.2)(0.5,0.2), (0.6,0.4)(0.6, 0.4)(0.6,0.4), and (0.9,0.8)(0.9, 0.8)(0.9,0.8). Each sub-space has its own codebook of 2b2^b2b representative sub-vectors, found by running k-means on the sub-vectors of the collection. With b=2b = 2b=2, each codebook holds four centers, and each sub-vector is replaced by the 2-bit number of its nearest center: 00, 10, 01, and 10. The code 10 appears twice but refers to different centers, because sub-spaces 2 and 4 have different codebooks. Instead of eight floats with 256 bits, the vector is stored in 8 bits, a compression of 1:32.

The search uses lookup tables. We split the query q\mathbf{q}q in the same way into q1,…,qm\mathbf{q}_1, \dots, \mathbf{q}_mq1​,…,qm​ and compute, for every sub-space jjj and every center of its codebook, the squared distance between qj\mathbf{q}_jqj​ and that center. This fills mmm tables with 2b2^b2b entries each, once per query. The approximate distance to a stored vector is then a sum of mmm table look-ups, one per code.

(1)

Here cj(p)\mathbf{c}_j(\mathbf{p})cj​(p) is the center of codebook jjj that represents the jjj-th sub-vector of p\mathbf{p}p. The query stays exact; only the stored vector is replaced by its centers, so each term is read from a table computed once per query.

Example

For our collection of one billion 768-dimensional vectors, we choose m=96m = 96m=96 sub-vectors of 8 dimensions each and b=8b = 8b=8 bits per code. Every vector becomes 96 bytes instead of 3,072, a compression of 1:32, and the whole collection needs 96 GB instead of 3 TB. Per query, the lookup tables hold 96×25696 \times 25696×256 entries, each a distance over 8 dimensions: 96×256×8≈197,00096 \times 256 \times 8 \approx 197{,}00096×256×8≈197,000 multiply-adds, as much as comparing the query with 256 full vectors. Against a billion stored vectors, this cost is negligible. Each stored vector then costs 96 look-ups and additions instead of 768 multiply-adds, and 96 bytes read instead of 3,072.

The standard choice is b=8b = 8b=8: each code is one byte, and each table of 256 entries fits into the processor cache. The sub-vector length then sets the compression. Sub-vectors of 4 to 16 dimensions give ratios between 16 and 64 times over 4-byte floats. Jégou and colleagues stored 128-dimensional SIFT image descriptors in 8 bytes, a ratio of 64. Longer sub-vectors compress more but approximate the distance more coarsely, which a final reranking step on the exact vectors compensates. At 96 bytes for 768 dimensions, PQ uses exactly one bit per dimension, and at 48 bytes only half a bit, a rate that scalar quantization cannot reach.

Locality-sensitive hashing¶

Locality-sensitive hashing (LSH), one of the first approximate methods from the late 1990s, maps vectors to bit strings. It chooses hhh hyperplanes and records for each one on which side a vector lies: bit jjj is 1 if the vector lies on the positive side of hyperplane jjj and 0 otherwise. In Figure 2, three hyperplanes divide the plane into seven regions. One of the eight possible 3-bit codes does not occur, because three lines cannot create more than seven regions in the plane. The query q\mathbf{q}q lies on the positive side of hyperplane 1 only, so its code is 100. Points in the same region share the query’s code, and points in a neighboring region differ from it in one bit.

The obvious way to use the codes is as hash buckets: return the points that share the query’s code. This fails as soon as hhh grows. With 64 hyperplanes there are 264 possible codes, far more than stored vectors, so most buckets are empty, and the query’s bucket is likely empty as well. LSH therefore ranks all stored codes by their Hamming distance to the query’s code, the number of bits in which they differ, and returns the vectors with the smallest Hamming distance. Comparing bit strings is extremely cheap: an exclusive-or followed by a count of the set bits. With h=256h = 256h=256 hyperplanes, a 768-dimensional vector shrinks from 3,072 bytes to 32 bytes, a factor of 96. Since the Hamming distance takes only h+1h + 1h+1 different values, many vectors tie, and an exact reranking of the best candidates resolves the ties.

The Hamming distance is a good proxy because it tracks the angle between vectors. For random hyperplanes through the origin, the probability that a hyperplane separates two vectors equals θ/π\theta / \piθ/π, where θ\thetaθ is the angle between them, so the expected Hamming distance is h⋅θ/πh \cdot \theta / \pih⋅θ/π. The hyperplanes in the figure are drawn freely to make the regions visible; the analysis assumes hyperplanes through the origin, the common choice in practice. Because LSH approximates the angle, it serves cosine similarity directly. For the dot product, the extension trick of Low-Dimensional Search Structures first gives all stored vectors the same length, after which ranking by angle equals ranking by dot product.

Why the Hamming distance tracks the angle (optional reading)

Consider two vectors x\mathbf{x}x and y\mathbf{y}y with angle θ\thetaθ between them, and a random hyperplane through the origin. The hyperplane separates the two vectors if they fall on different sides, which gives them different bits. Only the plane spanned by x\mathbf{x}x and y\mathbf{y}y matters for this question. The hyperplane cuts this plane along a line through the origin, and for a random hyperplane the direction of this line is uniformly distributed.

The line separates x\mathbf{x}x from y\mathbf{y}y exactly if it passes through the angle between them. A line through the origin covers two opposite directions, so it falls into the angle θ\thetaθ or into its mirror image on the other side of the origin. Both together cover 2θ2\theta2θ of the full circle of 2π2\pi2π, and the probability of a separating hyperplane is 2θ/2π=θ/π2\theta / 2\pi = \theta / \pi2θ/2π=θ/π. This argument is due to Charikar (2002), who introduced hyperplane hashing for the cosine.

With hhh independent hyperplanes, the Hamming distance is a count of hhh independent events with probability θ/π\theta / \piθ/π each. Its expected value is h⋅θ/πh \cdot \theta / \pih⋅θ/π, and its standard deviation is h⋅(θ/π)(1−θ/π)\sqrt{h \cdot (\theta / \pi)(1 - \theta / \pi)}h⋅(θ/π)(1−θ/π)​. For h=256h = 256h=256 and θ=π/4\theta = \pi / 4θ=π/4, the expected Hamming distance is 64 with a standard deviation of about 6.9. The estimate of θ/π\theta / \piθ/π is therefore accurate to about ±0.03\pm 0.03±0.03, and more bits make it more accurate.

The same reasoning explains the limits of LSH. Two vectors at angles of 0.24π0.24\pi0.24π and 0.26π0.26\pi0.26π to the query are hard to tell apart with 256 bits, which is exactly the situation inside a cluster, where the nearest neighbors are almost equally close. LSH finds the cluster reliably but not the order within it. This is why LSH results are usually reranked with exact vectors.

The second lever gains between a factor of 4 for 8-bit scalar quantization and roughly a factor of 100 for short LSH codes, with product quantization typically in between at 16 to 64. Every vector is still read, but each one costs only a fraction of a full comparison.

Fewer vectors read¶

The third lever reduces the number of vectors read. This was the idea behind the tree structures in Low-Dimensional Search Structures: skip regions that cannot contain the answer. The previous section showed that exact pruning fails in high dimensions, because the sphere around the query intersects every region. Approximate methods relax the requirement. They visit only the regions most likely to contain good matches and accept that a neighbor just across a boundary may be missed. Figure 3 contrasts the two approaches.

Inverted file¶

The inverted file (IVF) borrows the inverted index from text retrieval. A clustering algorithm, usually k-means, chooses nlistn_{\text{list}}nlist​ centers and assigns every vector to its nearest center, as in Figure 4. The index is a dictionary that maps each center to the list of its vectors, just as an inverted index maps each term to its posting list. A query is first compared with all centers, and the search then scans only the lists of the nproben_{\text{probe}}nprobe​ nearest centers. The share of the collection read is nprobe/nlistn_{\text{probe}} / n_{\text{list}}nprobe​/nlist​. For our billion vectors with nlist=4,096n_{\text{list}} = 4{,}096nlist​=4,096, each list holds about 244,000 vectors, and probing 16 lists reads 1/2561/2561/256 of the collection.

The parameter nproben_{\text{probe}}nprobe​ is the tuning knob. A neighbor that sits just across a cluster boundary is missed if its list is not probed, and each additional list recovers some of these misses. The cost grows linearly with the number of probed lists, while the gain in recall shrinks. The following measurements from the ann-benchmarks project, discussed below, use FAISS with 4,096 lists on 1.2 million GloVe word vectors with 100 dimensions:

Doubling the probes from 100 to 200 almost halves the throughput but adds only 4 points of recall. Even at 200 probes, the search is 18 times faster than the full scan, which manages 16.5 queries per second on the same hardware.

Navigable small-world graphs¶

A different approach navigates a graph. A navigable small-world (NSW) graph turns every vector into a node and links it to a fixed number of its nearest neighbors, its “friends”, plus some long-range links that act as shortcuts across the space. The graph has two key properties. It is navigable: from any node, a step to the neighbor closest to the query makes progress toward the query. And it is a small world: any two nodes are connected by a short path, whose length grows only poly-logarithmically with the number of nodes.

Search starts at an entry point and greedily moves to whichever neighbor is closest to the query, as traced in Figure 5. It stops when no neighbor is closer than the current node. This node is a local minimum of the distance on the graph, not necessarily the global one, which is why the result is approximate. To reduce the risk of stopping early, the search keeps a list of the best efsearchef_{\text{search}}efsearch​ candidates instead of a single node and expands all of them. A longer list costs more steps and finds better neighbors.

The hierarchical version, HNSW (Malkov and Yashunin, 2016), stacks several such graphs. The base layer contains all vectors. Each higher layer contains a random subset of the layer below, with fewer and fewer nodes toward the top. The search starts at the top, where few nodes and long links cover large distances in few steps. It then descends layer by layer, using the best node of each layer as the entry point for the next one, and refines the result on the base layer. Two parameters control the index: MMM, the number of links per node, and efsearchef_{\text{search}}efsearch​, the length of the candidate list. HNSW is among the fastest ANN methods and is included in most vector databases.

The speed has a price. The links need memory: with M=32M = 32M=32, the base layer stores about 64 links of 4 bytes per node, roughly 256 bytes per vector. Greedy steps jump to arbitrary nodes, so the vectors must reside in main memory. For our billion vectors, this means 3 TB of vectors plus 256 GB of links in memory. Building the graph is also slow, because every insertion runs a search to find the new node’s friends.

The graph and the inverted file combine well. Instead of single vectors, the base layer can hold clusters: the graph is built over the IVF centers, and each center points to its list. This matters when the number of lists is large. With nlist=65,536n_{\text{list}} = 65{,}536nlist​=65,536 lists for a billion vectors, comparing the query with every center already becomes noticeable, while a graph over the centers finds the nearest ones in a few steps. The search then scans the lists of the nproben_{\text{probe}}nprobe​ nearest centers, and its cost again grows linearly with the number of lists visited. In FAISS, the coarse quantizer IVF65536_HNSW32 implements this design. It also suits collections larger than main memory: the graph over the centers stays in memory, while the lists reside on disk.

Combining the levers¶

No single lever wins on its own, so production libraries combine all three. Facebook AI Similarity Search (FAISS) is the standard example. It organizes an index into four stages, which map directly onto the levers:

  • Vector transformers prepare vectors: PCA to reduce dimensions (lever 1), or L2-normalization for cosine search.

  • Coarse quantizers select the vectors to read, for example with IVF or HNSW (lever 3).

  • Fine quantizers encode the selected vectors compactly, for example with scalar quantization, PQ, or LSH (lever 2).

  • Refiners rerank the best k′k'k′ candidates with exact distances on the original vectors, or apply metadata filters.

A FAISS index type names its stages in this order. For our billion vectors, PCA384,IVF4096,PQ48,RFlat reduces the vectors to 384 dimensions, clusters them into 4,096 lists, encodes each vector into 48 bytes, and reranks the best candidates exactly. The codes of the whole collection take 48 GB and fit into main memory. Probing 16 lists reads 109/256≈3.910^9 / 256 \approx 3.9109/256≈3.9 million codes of 48 bytes each, about 190 MB per query. Reranking k′=100k' = 100k′=100 candidates reads another 300 KB of exact vectors from disk. Compared with the 3 TB of a full scan, the data read per query shrinks by a factor of about 16,000. The actual speed-up is smaller, because table look-ups, center comparisons, and random reads also cost time.

The levers compound their errors as well as their gains. PCA loses some information, PQ distorts the distances, and IVF misses neighbors in unprobed lists. Each error alone is harmless, but stacking several approximations can reduce result quality quickly. The parameters, here the target dimension, the code length, nlistn_{\text{list}}nlist​, nproben_{\text{probe}}nprobe​, and k′k'k′, must therefore be tuned together, by measuring the result quality on a sample of queries, ideally against relevance judgments rather than only against exact search.

Measuring the trade-off¶

Every ANN method exposes parameters that trade recall for speed: the number of probed lists in IVF, the candidate list length in HNSW, the code length in PQ and LSH. To compare methods fairly, we measure both axes at once. The quality axis is recall against the exact result.

The speed axis is throughput, in queries per second. Plotting throughput against recall traces a curve for each method, and the public benchmark at ann-benchmarks.com collects these curves for many libraries on standard datasets. Figure 6 shows the comparison on GloVe-100: 1.2 million word vectors with 100 dimensions, compared by cosine, with k=10k = 10k=10. Reading it is straightforward: fix the recall you need, then pick the method with the highest throughput at that recall. A method whose curve lies above another one dominates it.

Approximation buys two to three orders of magnitude, and the last few points of recall are the most expensive. The plot does not show everything, though. Memory use and build time appear in separate plots on the benchmark site, and they are where methods differ most: HNSW needs its graph and the full vectors in memory, while PQ needs a fraction of the memory and builds quickly.

Why does approximate search work?¶

The ann-benchmarks view makes approximation look costly. The last points of recall are expensive, and many cheap configurations return only a third of the exact top 10. But recall against exact search compares one retriever with another. A user never sees the exact top 10. The user sees the final result of a pipeline, and its quality is measured against relevance judgments with nDCG, as in Evaluating Graded Relevance.

We test this on TREC-COVID: 171,332 abstracts of COVID-19 research papers, 50 topics, and graded relevance judgments. The retrievers combine the three levers. Matryoshka embeddings from Qwen3-Embedding-0.6B are truncated to between 1024 and 64 dimensions. A full scan, IVF, or HNSW selects the vectors, and exact floats, PQ codes, or LSH bits compare them. This gives 140 retrievers. Each returns its top 50, and the cross-encoder Qwen3-Reranker-0.6B reorders them into the final top 10. TREC judged only the documents that the systems of 2020 retrieved, so the pool from Designing a Retrieval Benchmark misses documents that only an approximate retriever surfaces. An LLM judge graded these missing pairs. Otherwise they would count as not relevant and penalize exactly the retrievers we want to evaluate.

Figure 7 measures every retriever in three ways. We focus on the 126 retrievers that read at least 100 times less data than a full scan. Against exact search (left), their median recall@10 is 0.24, so the typical cheap retriever returns only a quarter of the exact top 10. By this measure, approximate search fails. Judged for relevance (middle), the same top 10 reach a median nDCG@10 of 0.80, against 0.91 for exact search. The documents they return instead of the exact neighbors are often just as relevant. This is the loss of contrast from The Curse of Dimensionality at work: the exact neighbors are only marginally nearer than the next candidates, and many of those candidates are good matches too. After reranking (right), the median rises to 0.88, against 0.92 for exact search, and 44 percent of the cheap retrievers end within 0.03 of exact search.

Figure 8 follows five retrievers through the pipeline. One retriever uses 256 dimensions, 16 of 1,024 IVF lists, and 32-byte PQ codes. It reads 608 times less data than a full scan and returns only a third of the exact top 10, yet after reranking it reaches an nDCG@10 of 0.92, the same as exact search. HNSW on 64-dimensional embeddings reads 2,604 times less data with the same result. Once a reranker follows, even aggressive Matryoshka truncation costs almost nothing.

The two remaining retrievers show where this stops. PQ with 8 bytes per vector distorts the distances so strongly that only 6 percent of the exact top 10 survive, and on its own it reaches an nDCG@10 of 0.66. Many relevant documents are still among its 50 candidates, so the reranker lifts the result to 0.80 and repairs more than half of the gap. IVF with a single probed list fails differently. It never reads the clusters next to the query’s own cluster, so the reranker never sees their documents, and the result stays at 0.86 before and after reranking. Fine-filter errors are repairable; coarse-filter errors are not. Production systems therefore keep the coarse filter generous, with enough probed lists or a long candidate list, and let the fine filter be aggressive.

There is no single best method, only the best operating point for a given collection, memory budget, and quality target. Recall against exact search is a useful diagnostic for one index, but the operating point should be chosen on end-to-end quality: the cheapest retriever whose reranked result stays close to that of exact search. The benchmark above covers one collection and one embedding model, so the operating point must be measured again for each application. HNSW is a strong default as long as the vectors fit into main memory. Beyond that, IVF with product quantization and a final reranking step is the common choice.
