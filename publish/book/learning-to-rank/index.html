Learning to Rank

The previous two sections produced a long list of signals: BM25F over several fields, proximity, anchor text, PageRank, site quality, location, and language. A real search engine adds many more, such as freshness, the URL depth, the share of users who clicked a page for similar queries, or the score of a neural reranker. Google has long described its ranking as built from hundreds of signals. All of them must be combined into one score per page, and the combination decides what the user sees.

This section starts with an example that combines four signals by hand and asks how to find the best combination. It then formalizes the question as a machine learning problem with three parts: the training data, the scoring model, and the loss. Finally, it shows how the models are trained and how search engines keep collecting the labels for training, mainly from the clicks of their users. The section closes with feeds, which use the same machinery to rank content without any query.

The Ranking Stack¶

No search engine applies its most expensive ranking function to billions of pages. Ranking happens in stages, and each stage hands a smaller candidate set to a more expensive model, as Figure 1 shows. The retriever uses the inverted index (4 - Index for Text Retrieval) and a cheap score such as BM25F to select on the order of ten thousand candidates. For each candidate, the system computes the full feature vector. A learned ranker, typically an ensemble of gradient-boosted decision trees, orders the candidates. A neural reranker, such as a cross-encoder (Semantic Similarity with Transformers), rescores the top hundred. Finally, the result page is composed from the ranked list and other elements such as ads and knowledge panels (The Web Search Landscape).

This section is about the learned ranker in the middle of the stack. Its input is one feature vector per query-page pair, and its output is a score used for sorting.

Adding proximity does not help, since the three pages that matter score almost the same on it. Adding PageRank or anchor text fixes the ranking. But three quite different weight vectors are now perfect, including one that uses the anchor text alone. This query cannot tell them apart. Other queries can: anchor text alone fails for a new page that nobody links to yet, and a high PageRank weight pushes strong home pages to the top even for queries that they match only weakly.

A good weight vector must therefore work on average over thousands of queries at once. It must cover hundreds of signals, not four, and it must be chosen again whenever the signals or the web change. Tuning by hand does not scale to this. Instead, we collect queries with judged candidates and let an algorithm search for the weights that rank them best. Learning to Rank (LTR) treats the combination of signals as a supervised machine learning problem: given examples of queries, candidate pages, and their known relevance, learn a function that orders the candidates well.

The Learning-to-Rank Problem¶

Figure 2 shows the three parts of the problem. A scoring model sθs_\thetasθ​ maps the feature vector x\mathbf{x}x of a query-page pair to a score sss, and sorting by sss gives the ranked list. The parameters θ\thetaθ of the model are not set by hand. They are learned from training data, a set of queries with candidate pages and labels yyy. The loss L\mathcal{L}L compares the scores with the labels and measures how well the model ranks: the better the ranking, the smaller the loss. Training updates θ\thetaθ until the loss is small, that is, until sorting by sss orders the candidates like their labels.

Since only the order of the candidates of one query matters, the loss is computed per query and summed over all training queries:

Training Data: Features and Labels¶

Each training example is a pair (Q,D)(Q, D)(Q,D) of a query and a candidate page, described by a feature vector xQ,D\mathbf{x}_{Q,D}xQ,D​ and a label yQ,Dy_{Q,D}yQ,D​. The training set is T={(Q,xQ,D,yQ,D)}\mathbb{T} = \{(Q, \mathbf{x}_{Q,D}, y_{Q,D})\}T={(Q,xQ,D​,yQ,D​)} over many queries, each with tens to hundreds of judged candidates. Features fall into three groups:

  • Query-dependent features describe how well the page matches the query: BM25F per field, proximity, anchor-text score, cosine similarity of embeddings (Building Semantic Search).

  • Query-independent features describe the page itself: PageRank, site quality, page length, URL depth, age.

  • Query features describe the query alone: its length, its intent class, whether it names a place. They do not separate the candidates of one query, but they let the model weight other features differently for different kinds of queries.

The label yQ,Dy_{Q,D}yQ,D​ says how relevant DDD is for QQQ. The classic source is human judgment on a graded scale, as in our table. Search engines employ thousands of trained raters who judge pages according to detailed guidelines. The second source is user behaviour, mainly clicks. Both sources are discussed in Labels for Continuous Training.

The Scoring Model¶

The scoring model decides which combinations of signals the ranker can express at all. Three model families are common, shown in the middle of Figure 2.

A linear model computes the weighted sum of our hand-tuned attempts, sθ(x)=w⊤xs_\theta(\mathbf{x}) = \mathbf{w}^{\top} \mathbf{x}sθ​(x)=w⊤x with θ=w\theta = \mathbf{w}θ=w. It has one weight per signal, is cheap to evaluate, and its weights are easy to read. But each signal adds its contribution regardless of the other signals. A linear model cannot express that a high PageRank should count only if the page also matches the query well. Without that condition, a strong home page outranks better pages for every query that it matches even weakly.

A regression tree captures such interactions. It asks a sequence of threshold questions about the features and returns the value stored in the leaf it reaches. A tree with three questions reproduces the grades of our four pages exactly. It first asks whether the anchor score exceeds 3. If so, it asks whether PageRank exceeds 0.8 and returns 3 (d1d_1d1​) or 2 (d4d_4d4​). If not, it asks whether proximity exceeds 0.5 and returns 1 (d2d_2d2​) or 0 (d3d_3d3​). PageRank is used only for pages with strong anchor text, which is an interaction that no single weight can express. A single tree is coarse, so rankers use a tree ensemble that adds up the outputs of hundreds of small trees, sθ(x)=∑m=1Mfm(x)s_\theta(\mathbf{x}) = \sum_{m=1}^{M} f_m(\mathbf{x})sθ​(x)=∑m=1M​fm​(x). In gradient-boosted decision trees (GBDT), each new tree fmf_mfm​ is trained to correct the remaining errors of the trees before it. Trees also handle features on different scales and missing values without manual feature engineering. They do need features that mean the same for every query, since one threshold such as “BM25F > 5” applies to all queries alike. A query with rare terms produces high BM25F scores because of their IDF, and a query with frequent terms produces low ones, so a score of 5 can be mediocre for the first and excellent for the second. Learning-to-rank benchmarks therefore scale each query-dependent feature to the range 0 to 1 within the candidates of each query.

A neural network learns the interactions in its hidden layers. A small multi-layer perceptron computes sθ(x)=w2⊤ ReLU(W1x+b1)s_\theta(\mathbf{x}) = \mathbf{w}_2^{\top} \, \text{ReLU}(\mathbf{W}_1 \mathbf{x} + \mathbf{b}_1)sθ​(x)=w2⊤​ReLU(W1​x+b1​), with all weight matrices and vectors in θ\thetaθ. A cross-encoder (Semantic Similarity with Transformers) goes one step further: it reads the text of the query and the page directly instead of a feature vector, and learns its own features.

The three families trade expressiveness against cost and transparency. Tree ensembles are the strongest choice for hand-crafted features such as those in our table, and they sit in the middle of the ranking stack. Cross-encoders are the most expressive, but also the most expensive, so they only rescore the top candidates.

The Loss: Three Ways to Learn a Ranking¶

The loss decides what the training optimizes. LTR methods differ in what they treat as one training example and in the loss they minimize. Figure 3 compares the three families on the same four documents.

Pointwise: Predict the Grade¶

The pointwise approach ignores that we want a ranking. It treats each (Q,D)(Q, D)(Q,D) pair on its own and trains a regression model to predict the grade yyy, or a classifier to predict the grade class. Any standard learner works, for example least-squares regression with the loss L=∑D(sθ(xQ,D)−yQ,D)2\mathcal{L} = \sum_{D} \big(s_\theta(\mathbf{x}_{Q,D}) - y_{Q,D}\big)^2L=∑D​(sθ​(xQ,D​)−yQ,D​)2. On our four pages, a linear model reproduces the grades 3, 1, 0, 2 exactly, but with the weights (0.13,0.65,0.73,−3.16)(0.13, 0.65, 0.73, -3.16)(0.13,0.65,0.73,−3.16). A negative PageRank weight makes no sense: four examples and four free weights can fit any grades, so a perfect fit on so little data says nothing about which signals matter.

The pointwise view has two weaknesses. First, it spends effort on the wrong goal. Predicting 4.0 instead of 3 for d1d_1d1​ costs a squared error of 1.0, but it is harmless, since d1d_1d1​ stays on top. Predicting 1.6 for d4d_4d4​ and 1.7 for d2d_2d2​ costs only 0.16+0.49=0.650.16 + 0.49 = 0.650.16+0.49=0.65, yet it swaps two pages. Second, grades are not comparable across queries. For a query with one perfect page, a grade of 2 may be the second-best result. For a query with fifty perfect pages, the same grade lands on page three. Only the order within a query matters.

Pairwise: Order Each Pair¶

The pairwise approach turns ranking into classification of pairs. For each query, every pair of documents with different grades becomes one example: did_idi​ should rank above djd_jdj​, written di≻djd_i \succ d_jdi​≻dj​, if yi>yjy_i > y_jyi​>yj​. Our four pages yield six such pairs: d1≻d2d_1 \succ d_2d1​≻d2​, d1≻d3d_1 \succ d_3d1​≻d3​, d1≻d4d_1 \succ d_4d1​≻d4​, d2≻d3d_2 \succ d_3d2​≻d3​, d4≻d2d_4 \succ d_2d4​≻d2​, and d4≻d3d_4 \succ d_3d4​≻d3​. A model that orders every pair correctly produces the ideal ranking.

The pairwise view is much closer to the ranking goal, and it produces many training examples from few judgments. Clicks also naturally produce pairs, as we will see. Its weakness is that every pair counts the same. Swapping the pages at ranks 1 and 2 hurts the user far more than swapping the pages at ranks 40 and 41, but both cost the same in L\mathcal{L}L.

Listwise: Optimize the Ranking Measure¶

The listwise approach optimizes a measure of the whole ranked list, such as nDCG. The difficulty is that nDCG depends on the sorted order, so it changes in jumps when two scores cross and has no useful gradient. LambdaRank (listwise, built on RankNet’s pairs) solves this with a simple trick. It keeps the pairwise gradients of RankNet, but scales the gradient of each pair by how much nDCG would change if the two documents swapped positions in the current ranking:

Pointwise, pairwise, listwise: what is the training example?

The three families are not model types. Any of the scoring models above (a linear function, trees, or a neural network) can be trained with any of the three losses. What differs is the unit of training and the loss: one document and its grade (pointwise), one pair and its order (pairwise), or one whole result list and its nDCG (listwise).

Learning to Rank in Practice¶

The formalization leaves two practical questions. How does an algorithm find the parameters θ∗\theta^*θ∗ for a given model and loss? And where do the labels come from, not once, but continuously, as the web and its users change?

Training the Model¶

For a linear model or a neural network, training uses gradient descent, as for the word embeddings of Word Embeddings. For a linear model with the RankNet loss, each pair pulls the weights in the direction of the feature difference xi−xj\mathbf{x}_i - \mathbf{x}_jxi​−xj​ between the better and the worse page. The pull is strong if the pair is currently mis-ordered and weak if it is already well separated:

With thousands of queries, the gradient sums the pulls of all their pairs, and the weights settle on a compromise that ranks well on average. Trees cannot be trained by gradient descent on their parameters, since their thresholds and leaf values do not change smoothly. LambdaMART (LambdaRank trained with decision trees) combines the lambda weights with MART (multiple additive regression trees), a form of gradient-boosted decision trees. LambdaRank defines what to optimize: the lambdas. MART defines how the model grows: each new tree is fitted to the lambdas of the current ensemble, so the ensemble grows in the direction that improves nDCG most. LambdaMART won the Yahoo! Learning to Rank Challenge in 2010 and remains a strong baseline for ranking over many hand-crafted features. Libraries such as LightGBM and XGBoost implement it with a lambdarank objective.

Gradient-boosted trees over hand-crafted features dominated web ranking in the 2000s and early 2010s. Since 2019, transformer models have taken over a growing part of the stack. Google announced in 2019 that it uses BERT to understand queries and rank results, affecting about one in ten English queries in the US at launch. A cross-encoder reads query and page together and captures meaning that no feature vector expresses, for example that “can you get medicine for someone pharmacy” is about picking up a prescription for another person. Neural rankers have not replaced learning to rank; they have joined it. A neural reranker is trained with the same pointwise, pairwise, or listwise losses, often on the same mix of human labels and clicks. Its output can become one more feature for a tree ensemble, or the final stage of the stack in Figure 1.

Labels for Continuous Training¶

A ranker is never trained only once. New pages appear, events create new queries, the meaning of queries shifts, and every new signal requires a new model. Search engines therefore retrain their rankers regularly, and they need a steady supply of fresh labels. Two sources provide them.

Human raters judge query-page pairs on a graded scale, following detailed guidelines. Their labels are precise and reflect the intended notion of quality, but they are slow and expensive. Search engines therefore spend them where precision matters most: on test sets that evaluate every new ranker offline with nDCG (When Evaluation Misleads), and on hard or new kinds of queries.

User behaviour is the second source: which results users click, how long they stay on the clicked page, and whether they return to the result list to try another result. Clicks are abundant and free, and they reflect the needs of real users rather than the opinion of raters. Every day of traffic adds millions of new examples. They are also heavily biased.

The strongest bias is position bias. Users click the top results much more often, partly because they are better, but mostly because they are on top. In an eye-tracking study, Joachims et al. swapped the first two results without telling the users, and the result at rank 1 still received most clicks. A click on rank 1 is weak evidence of relevance; a click on rank 5 is strong evidence, since the user read past four other results to get there. Joachims’s early solution used clicks to create pairwise preferences: if the user skipped the result at rank 2 and clicked the one at rank 3, then d3≻d2d_3 \succ d_2d3​≻d2​ for this query. These pairs feed directly into a pairwise learner such as RankNet.

Modern unbiased learning to rank corrects position bias explicitly. It estimates the probability pkp_kpk​ that a user even looks at rank kkk, the propensity, for example through small randomized swaps in a fraction of the result pages. Each click at rank kkk is then weighted by 1pk\frac{1}{p_k}pk​1​ in the loss, so clicks at rarely viewed positions count more. Under the assumption that users click a result exactly when they see it and find it relevant, this inverse propensity weighting removes the position bias in expectation.

Clicks are not relevance

A click shows that a result looked promising in the result list, not that the page satisfied the user. Attractive titles and thumbnails earn clicks regardless of quality, which rewards clickbait. Search engines therefore use refined signals: long dwell time on the clicked page counts as success, while a quick return to the result list (a “pogo-stick” back to the results) counts as failure. Even so, a model trained on clicks optimizes what users click, which is not always what is good for them. We meet this tension again in Ranking Without a Query: Feeds.

Clicks also decide whether a new ranker goes live. Offline metrics on a judged test set cannot capture everything. Search engines therefore run online experiments: an A/B test shows the new ranker to a small fraction of users and compares click and satisfaction metrics with the current one. Interleaving mixes the results of both rankers into one list and checks which ranker’s results attract more clicks; it needs far fewer users than an A/B test to detect a difference.

Together, these steps form a loop. The deployed ranker produces result pages, the result pages produce clicks, the debiased clicks train the next ranker, and online experiments decide whether it replaces the current one. The loop has a blind spot: users can only click what the ranker shows, so a page that never reaches the first result page never collects the clicks it would need to get there. The randomized swaps that estimate propensities also help here, since they show some results at positions where the current ranker would not put them. The same staged design and the same loop also power recommendation feeds, which we turn to next.

Ranking Without a Query: Feeds¶

Open TikTok, YouTube, Instagram, or X, and the app shows content before the user types anything. Every swipe asks the same question as a search engine: of the hundreds of millions of items available right now, which few should this user see next? The difference is where the information need comes from. In web search, the user pulls information with a query. In a feed, the system pushes content, and the user’s history, social connections, and context take the role of the query. For videos, music, and images, this has become the main way people discover content.

A feed reuses the machinery of this chapter and of earlier chapters almost unchanged, in the same staged design as the web ranking stack (Figure 4):

  • Candidate generation takes the place of the retriever. One source is embedding retrieval: a two-tower model encodes the user and every item into one vector space. This is the bi-encoder of Semantic Similarity with Transformers with the user in the place of the query, and an approximate nearest-neighbour index (Approximate Nearest-Neighbor Search) returns the closest items in milliseconds. Since the item vectors are computed from the content, a new video can be recommended before anyone has watched it; the multimedia features of later chapters feed exactly this step. A second source is the social graph: Personalized PageRank and SALSA (Link Analysis: PageRank and HITS) find the accounts closest to a user, which yields “who to follow” suggestions and the posts that these accounts liked.

  • Ranking is learning to rank. A heavy ranker predicts, for each candidate, the probability of every possible reaction: like, reply, share, watch to the end, hide, or report. This is pointwise learning to rank with several labels at once, and the predictions are combined in a weighted sum.

  • Filters remove content the user has already seen or blocked, limit the number of posts per author, and mix in new creators and topics.

The weights of the sum are a product decision, not a learned quantity, and they decide what the feed becomes. X, which published the source code of its home timeline in 2023, weighted a like with 0.5, a reply with 13.5, and a reply that the post’s author engages with 75. Such weights favour conversations; high weights on shares or watch time favour content that spreads. The warning about clicks applies here with full force. Replies, shares, and watch time correlate with interest, but outrage and sensational content produce them as well. A feed trained purely on engagement can amplify divisive content and narrow what a user sees into a filter bubble. Platforms counter this with negative feedback signals, quality classifiers, diversity rules, and surveys that ask users directly whether a post was worth their time.

Feeds also face sharper versions of the evaluation problems of web search. The log only shows reactions to what the current system chose to show, so a feed reserves part of its slots for exploration, such as new creators and new topics, to learn anything new about its users. And since there is no ground truth for which post a user should have seen, feeds are evaluated almost entirely online, with A/B tests that track long-term effects such as whether users return next week, not only short-term engagement. Search and feeds thus share the same end point: both learn to rank from user behaviour, and both must keep the measured behaviour from replacing the goal it stands for.
