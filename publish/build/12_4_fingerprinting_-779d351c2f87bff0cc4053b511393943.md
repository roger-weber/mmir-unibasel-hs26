# Fingerprinting for Music Recognition

Identifying a song from a real-world audio recording presents fundamental challenges that the previous approaches cannot overcome easily. When you record a song in a noisy place, such as a restaurant with conversation, a crowded bar, or a moving vehicle, the captured audio is very different from the studio-quality reference recording in a database. Background noise, compression artifacts, and acoustic distortion all change the audio signal, so you cannot simply compare waveforms or spectral envelopes directly.

The main challenge is achieving robustness by finding invariant features. A song's recognizable core, its melody and harmony, survives many distortions, but that core must be extracted so it stays stable across different kinds of degradation. Traditional frequency-domain analysis keeps too much detail: amplitude, phase, and exact frequency positions all change with noise and recording conditions. A fingerprinting system must use features that resist these changes while remaining specific to each song.

Audio fingerprinting is a content-based identification method that lets apps like Shazam recognize songs from short real time recordings, even with a lot of noise or distortion. Instead of comparing whole audio files, it extracts small features that resist noise and capture a song's frequency and timing patterns. This allows identification from a brief microphone recording in a busy restaurant or while driving. Modern audio fingerprinting works because reference recordings are pre-cataloged. Systems preprocess each song's official recordings to create a compact fingerprint. When a query recording arrives, the app makes a fingerprint from it and searches the database for the best matches.

This approach immediately suggests its fundamental limitations:

  - Singing Your Own Version: Fingerprinting systems are built to match pre-recorded, cataloged recordings. When you sing a song yourself, you introduce large changes in pitch stability, vibrato, timing, and spectral content. Your voice produces a very different frequency pattern than the original track. Fingerprint extraction relies on features like instrumental arrangement and precise timing, which change a lot in a vocal performance.

  - Live Recordings: Live performances differ from studio recordings in ways that exceed fingerprinting's robustness. They can use different instruments, change tempo, include extended improvisations, and contain substantial audience noise. Shazam can sometimes recognize live versions when they stay close to the original, but most live performances differ too much in their time and frequency characteristics to reliably match the fingerprints in the database. The system was trained on the assumption that recordings preserve the song's core frequency structure, an assumption live performances often violate.

Step 1: Computing the Spectrogram

  - We first transform the audio into a spectrogram using the Short-Time Fourier Transform (STFT). The recording is split into overlapping short time windows. For each window, the FFT shows which frequencies are present and their amplitudes. The result is a 2D image where the horizontal axis is time, the vertical axis is frequency, and color shows the energy at each time and frequency point.

  - The spectrogram is the key intermediate representation because it reveals the noise problem. Pure background noise shows up as uniform energy across many frequencies and time frames, while the signal of interest, the actual song, appears as localized peaks of high energy concentrated at specific frequencies and times.

Step 2: Identifying Constellation Map Peaks

  - Next is peak detection. This step finds peaks in the spectrogram that correspond to the most prominent frequency components. Instead of using every frequency value, which would create a huge, noise-sensitive fingerprint, Shazam keeps only the local maxima: points whose energy is higher than all neighbors in both time and frequency.

  - This produces a sparse set of points, called the constellation map, that characterizes the song's structure. Background noise produces random peaks across the spectrogram, but these noise peaks are usually weaker and less concentrated. The strongest peaks, those that meet the local-maximum criterion, tend to match real signal features such as instrument harmonics. Isolated weaker noise peaks are filtered out by the peak detection process, even when background noise is high.

  - The result is a noise-robust representation that captures the song's main frequency structure while removing high-frequency noise and weaker spectral features.

Step 3: Combinatorial Hashing

  - Constellation maps are much smaller than full spectrograms, but they still contain many isolated peaks, so direct matching is slow. A 5 to 10 second query can produce hundreds or thousands of peaks. Comparing each of those to billions of stored peaks across millions of songs would be computationally expensive.

  - Shazam uses combinatorial hashing. Instead of storing or matching single spectral peaks, it makes fingerprint hashes by pairing peaks. The procedure is:

    - Anchor point selection: Each peak in the constellation is chosen as an anchor point.

    - Target zone definition: For each anchor point, a target zone is set in the time-frequency space after the anchor point, for example within the next 20 to 40 frequency bins and the next 50 to 200 ms.

    - Hash generation: The anchor point is paired with every other peak inside its target zone. For each pair the algorithm records the first peak's frequency, the second peak's frequency, and the time difference between them.

    - Hash encoding: These three values are combined into a single compact hash, typically a 32-bit integer, using quantification. The hash serves as a fingerprint for that pair relationship.

  - This method is clever because it turns the matching task into simple hash table lookups much like inverted files for classical text retrieval. Instead of comparing thousands of individual peaks, the system only looks for hashes that appear in both the query fingerprint and the database fingerprints. Because each hash encodes relative frequency and timing, the same pair relationships will produce identical hashes even if peak positions move slightly from noise or distortion.

  - The combinatorial structure gives inherent robustness. If a few peaks are lost to noise and removed from the constellation, many hash relationships stay the same because they involve other peaks. If a few noise peaks are added, they mainly produce hashes that are not in the database, so they do not match and are ignored.

Step 4: Query Fingerprinting

  - When a user taps the Shazam button, the system records a 5 to 10 second audio sample and processes it the same way as catalog songs. The result is a query fingerprint: a set of hashes that represent the recording's acoustic structure.

Step 5: Database Matching and Score Aggregation

  - Hash Matching: Shazam looks up each hash from the query fingerprint in a table that holds every hash from the song catalog. The table also stores metadata showing which song each hash belongs to and the hash's position (time) in that recording. For each query hash, the system retrieves all matching entries from the database.

  - Score Aggregation: The main point is that many query hashes will match many catalog songs by chance or because of similar harmonic patterns. What matters is that hashes from the correct song will line up in time. For each candidate song:

    - 1. For each matching pair of hashes (query and database hash), compute the time offset as $t_{track} − t_{sample}$. This offset shows where in the original song the query sample most likely occurs.

    - 2. Build a histogram of the candidate song's time offsets. If the query comes from that song at a specific position, most matching hashes will vote for the same offset.

    - 3. The score for the song is the height of the largest histogram bin, the number of hashes that agree on a single time offset.

    - 4. The song with the highest score is returned as the match.

This voting mechanism effectively filters out noise and false matches. Accidental hash collisions happen at random time offsets and make a flat histogram. True matches group their votes at a specific offset and make a clear peak.
